# Redis 用户业务缓存隔离候选

用户已确认此有限改动：仅在隔离环境验证用户/积分/签到相关缓存组不持久化，其他 Redis 缓存保留；添加严格默认关闭的适配检查。生产缓存、账号与签到写入开关不变。本批基于草稿 PR #5 的隔离恢复测试，不替代其待完成审查和剩余 P2 门槛。

## 原因与方案

前批实际复现：WordPress 原生元数据在 SQL 事务内写入后，当前连接的读取可把未提交积分写进共享 Redis；另一个 PHP 进程能读到临时值，SQL 回滚不撤销 Redis 值。只在事务结束时清缓存仍存在中间泄漏窗口。

使用 Redis Object Cache 原有 `WP_REDIS_IGNORED_GROUPS` 启动配置，将以下组对**所有 WordPress 请求**设为请求内缓存：

- `users`、`userlogins`、`useremail`、`userslugs`：原生用户及登录索引。
- `user_meta`：原生积分、经验、签到计数、角色及会话元数据。
- `zib_option_meta_data`：子比合并的用户数据、流水、签到记录，同时还包含部分主题配置/文章元数据。

因此会增加这些组的数据库读取；子比组不只包含用户内容，不能声称其他主题元数据缓存完全不受影响。其他未排除组继续跨请求复用 Redis，测试用独立内容组验证这一点。没有修改主题/Redis 插件源码，没有在事务前后临时切换全局缓存对象或绕过 SQL/回执校验。

官方能力说明：[Redis Object Cache 忽略缓存组](https://github.com/rhubarbgroup/redis-cache/blob/develop/FAQ.md#how-can-i-ignore-a-cache-group)。具体合同以本批安装的 3.0.0 代码与隔离结果为准。

## 默认关闭与检查

Bridge 0.3.1 新增 `includes/cache-policy.php`。没有外部缓存标志时还须核对实际对象来自 WordPress 内置缓存类文件，防止仅更改全局标志绕过检查；有持久缓存时，必须同时满足：

1. 私有启动配置明确 `DUANAP_HUB_CACHE_PROFILE='redis-user-local-v1'`。
2. `WP_REDIS_IGNORED_GROUPS` 在加载 WordPress 之前就包含上述六组；仅运行时添加组不接受。
3. 当前对象为已核对来源的 `WP_Object_Cache`，drop-in 版本 3.0.0，文件与已安装官方插件的 drop-in 一致，连接状态正常。
4. 运行时六组既在忽略列表中，实际 `group_type` 也均为 `ignored`。

任何检查失败继续返回 `hub_checkin_cache_unverified`，不增加“强制忽略错误”的开关。不写入配置、不自动安装/更换缓存组件。原有 Hub/Bridge 写入开关、主题/数据库/业务钩子检查仍然独立生效。

配置形式（**目前仅隔离环境**）：

```php
define('DUANAP_HUB_CACHE_PROFILE', 'redis-user-local-v1');
define('WP_REDIS_IGNORED_GROUPS', [
    'users', 'userlogins', 'useremail', 'userslugs',
    'user_meta', 'zib_option_meta_data',
    // Preserve any other groups already excluded by the site's configuration.
]);
```

不把此常量加入 Hub `.env.local`：它是 WordPress 私有启动策略。不要从请求参数、用户 Cookie 或 Studio 普通用户权限决定缓存策略。

## 验证范围

测试只使用标记开发库、合成用户、独立临时 Unix socket Redis、独立前缀，TCP 为 0。包括：

- 开关缺失、未知策略、六组逐项缺失、运行时分类异常、仅运行时添加组、未知缓存对象、drop-in 改变、外部缓存标志与实际对象不符时拒绝。
- 启用前遗留在 Redis 的错误用户/主题值不再被采用；非业务组继续跨 PHP 进程复用。
- 原生积分及主题流水在事务内对写入连接可见，另一进程只看到已提交值；回滚后没有共享临时值。
- 原生奖励、回执同一事务提交，新进程立即读取已提交余额/流水；同日重试保留回执且不再发奖；回执 SQL 失败时业务与缓存均回滚，重试仅发一次。

## 未来生产启用与回退边界

此批不执行生产操作。将来仍需先完成最终组合备份、审查及受限账号验收：

1. 冻结所有签到入口，包括博客原生入口；仅关闭 Bridge 统一写入会恢复原生处理，不能当作全站停发。
2. 将策略作为站点级私有启动配置部署，保留既有忽略组；等待旧请求结束并刷新 PHP worker/字节码配置，确认所有请求一致。不能只在某一 API 路径或某一实例开启。
3. 使用新的独立缓存前缀完成切换验证，避免重新采用旧组缓存；不使用 `FLUSHALL`，不清其他站点缓存。前缀轮换会使缓存暂时变冷。
4. 核对真实用户读取、权限、恢复、回执与同日并发后，才独立决定受限开启写入。QQ 审核、邮件和其他未完成门槛继续保留。
5. 回退先冻结写入、处理未决回执，再回退代码。恢复持久化用户组之前必须换新前缀或完成精确失效并验证，不能让旧缓存复活。保留业务账本，不用旧积分数据库覆盖新交易。

Redis/主题/Provider/Bridge 升级、其他插件改变业务钩子或缓存分类后须重新验收。未知后端/版本继续拒绝写入，性能权衡与生产上线不由测试脚本自动决定。
