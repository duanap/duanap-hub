# duanap Hub 需求规格与技术架构基线 V1.0

> **文档状态：** 需求基线已确定；部分第三方能力待技术验证  
> **整理日期：** 2026-10-10  
> **适用范围：** `duanap.cn`、`blog.duanap.cn`、个人小游戏、QQ 机器人及未来工具模块  
> **定位：** 面向逐步实施、验收、维护和交给 Codex 的统一依据。文中示例 URL、接口、表名并不代表已经上线。

> **身份决策更新（2026-10-16）：** 用户选择主站独立注册、登录和账号恢复，关联博客后解锁签到；本地方案细节见 [P2 独立账号决策](P2-INDEPENDENT-ACCOUNTS.md)。此决定覆盖本文旧段落中“WordPress 全权管理主站登录身份”的合同，积分/签到/流水仍由博客权威记录，历史会员数据不得自动导入。

## 1. 产品定位与建设目标

将 `duanap.cn` 建设为**小而美的个人数字门户（duanap Hub）**，统一展示公开个人信息、项目与小游戏、博客动态、实用工具，同时提供普通用户的统一登录、积分签到、游戏数据关联能力。

- **一级域名是主要品牌入口：** 首页简洁，项目、游戏及工具具备可独立收录的内容详情页。
- **主站账号独立，博客继续管理业务账本：** 主站维护本地账号、密码、恢复和会话；用户明确关联博客后，由博客唯一管理签到、积分和流水，主站经授权 API 读取并提交签到。
- **小游戏有独立业务边界：** 玩法、房间、背包、战绩由对应游戏服务维护，统一账号只负责关联身份。
- **QQ 机器人是另一种交互入口：** 与网页共用账号绑定和部分游戏业务，不重复维护修仙角色。
- **一切可展示内容尽量后台可编辑：** 非技术修改无需重新部署，新增复杂业务模块才需要开发代码。
- **技术克制：** 优先复用已有工程；不使用 Docker，不强制依赖 GitHub Actions/CI，不为了未来可能的规模提前引入微服务或复杂队列。

### 1.1 V1 必须达成的结果

1. 个人主页、公开资料、社交入口、作品导航和备案完整可用。
2. 后台采用精简分组导航及卡片式管理，支持内容、模块与首页编排。
3. 项目可维护介绍、手动状态、当前版本、更新日志、更新预告、开发路线图及游戏规则。
4. 主域名具有完整的 SEO 元信息、动态 Sitemap、robots、RSS 和搜索平台接入基础。
5. WordPress 身份和积分的统一接口边界得到验证，后续可安全接入主站和机器人。
6. 已有站点和游戏数据不因改版丢失，升级可回滚。

### 1.2 不作为首期目标

不建设任意上传代码的插件商城、复杂微服务、跨系统共享数据库写入、实时全球排行榜平台、自动化积分经济系统或完整社交网络。完整 QQ 机器人修仙、统一游戏战绩及工具矩阵分阶段交付。

## 2. 当前资产与迁移前提

| 资产 | 已知情况 | 处理原则 |
| --- | --- | --- |
| `blog.duanap.cn` | WordPress + 子比主题，拟作为用户和积分中心 | 保留现有博客、文章及用户数据；先只读审核再开发桥接插件 |
| `duanap/duanap-index` | Next.js 16、React 19、TypeScript、SQLite；已有主页、后台、SEO、备案、媒体、备份等能力 | **优先考虑复用**，在原功能上渐进改造 |
| `duanap/index` | 另一套 Astro + EmDash 工程，亦配置过主域名与独立会员能力 | 先确认其生产使用情况，不与 Next.js 主站盲目合并 |
| Hearts、梦幻三P、双人麻将等 | 各自独立游戏服务、身份或重连实现 | 保留规则引擎及旧玩家数据，增量接入统一身份 |
| 宝塔 / Nginx / EdgeOne | 既有部署基础设施 | 延续当前运维习惯，核验源站路由、缓存和安全策略 |

**当前源码已确认的差距：** `duanap-index` 目前通过 `app/sitemap.ts` 仅输出首页；`lib/seo.ts` 的首页标题与描述仍主要来自代码常量；旧后台在每个页面保留右侧预览栏。上述属于待改造的代码现状，不代表当前生产站点必然运行这一提交。

**上线前必须核实：** 当前一级域名真正部署的仓库、提交版本、生产数据库及持久化路径；博客的 WordPress / PHP / 子比 / 数据库版本；现有第三方登录方式；备份是否能实际恢复。仓库文件描述不等同于生产现状。

## 3. 整体技术架构

```text
访客 / 已登录用户 / 搜索引擎
              |
        EdgeOne / Nginx
              |
    +---------+--------------------+
    |                              |
 duanap.cn                     blog.duanap.cn
 Next.js 主站                  WordPress + 子比
 - 公开门户                    - 用户/第三方身份
 - duanap Studio 后台          - 签到/积分/积分流水
 - SEO / RSS / Sitemap         - 原创博客文章
 - 项目/工具内容               - duanap-hub-bridge 插件
 - SQLite + 媒体               - MySQL 或 MariaDB
    |                              ^
    +------ 服务端授权 API ---------+
    |
    +--> 各小游戏：独立规则引擎、房间、角色、战绩
    |                ^
    +--> QQ Bot 适配器 -- 修仙等共享游戏 API
    |
    +--> 只读外部适配器：EdgeOne / GitHub / 搜索平台
```

### 3.1 核心原则

- **模块化单体主站：** 主站 UI、后台、公开内容、SEO 及基础 API 同属一个 Next.js 应用，内部按模块划分，不拆成多套进程。
- **WordPress 业务桥接：** 单独开发 `duanap-hub-bridge` 插件，尽量通过子比已公开或可稳定复用的业务钩子完成操作；不直接在 Next.js 里修改 WordPress 表。
- **单一数据权威：** 每类数据只有一个负责写入的服务；跨系统通过 API 和稳定身份标识关联。
- **失败隔离：** EdgeOne、GitHub、博客文章同步等失败不阻断公开主页；积分发奖失败不得假装成功。
- **先实现接口约定，再实现扩展：** 预留模块注册和 Widget 槽位，但不做通用可执行插件平台。

### 3.2 域名与路由规划

| 地址 | 职责 | 索引策略 |
| --- | --- | --- |
| `https://duanap.cn/` | 个人主页、主入口 | 可收录 |
| `/about` | 完整公开个人介绍 | 可收录 |
| `/projects`、`/projects/[slug]` | 项目列表与详情 | 可收录 |
| `/games` | 小游戏中心 | 可收录 |
| `/tools`、`/tools/[slug]` | 在线工具中心与独立工具 | 可收录 |
| `/updates`（按需） | 已发布项目动态汇总 | 有充分内容时收录 |
| `/account`、`/account/*` | 用户资料、积分、绑定、战绩 | 私有、不可收录 |
| `/duanap`（现有路径，可保留） | 站点管理后台 | 必须鉴权、不可收录 |
| `/api/*` | 业务接口 | 不作为搜索内容 |
| `/robots.txt`、`/sitemap.xml`、`/feed.xml` | SEO 与订阅 | 公开访问 |
| `https://blog.duanap.cn/` | 博客原文、用户及积分业务 | 博客独立收录 |
| 各游戏子域名 | 独立游戏前端与实时服务 | 由各游戏配置决定 |

暂不新增独立 `auth.duanap.cn`。如果 WordPress 无法安全承担标准化 OIDC 身份提供方，再评估专用认证服务。**不要同时维护 WordPress 会员、EmDash 会员和新建 Hub 会员三套权威身份。**

## 4. 前台功能需求

### 4.1 关于我（About）

- 展示昵称、头像、公开身份、简介、技能方向、认证及可公开的经历。
- 社交入口整合 GitHub、QQ 或其他主动公开的平台，以及公开邮箱。
- 支持模块启停、排序、显示范围及独立编辑。
- 对不准备公开的资料，不采集或不在公共接口返回。

### 4.2 项目与作品（Projects）

每个项目都可拥有名称、slug、Logo/封面、类型、简介、详细介绍、截图、在线地址、仓库地址、标签、显示顺序及 SEO 信息。

**项目运营状态由管理员手动维护，不代表自动探测结果：**

| 状态 | 对外含义 |
| --- | --- |
| 开发中 | 尚在开发，可展示预告和路线图 |
| 正常开放 | 可以公开访问或使用 |
| 维护中 | 临时升级维护，可显示原因和预计恢复时间 |
| 暂停开放 | 暂停使用，保留介绍和历史记录 |
| 已停止维护 | 不再持续更新，保留档案 |

**把内容发布状态与运行状态分开：** 草稿、已发布、已下架决定内容是否公开；开发中、维护中等只描述运营情况。维护中可按配置隐藏或保留“进入项目”按钮；不应自动删除已经收录的项目详情页。

项目需支持四种内容：

1. **当前版本：** 版本号、发布日期、简短变更概要，可使用 `v1.2.0` 等自由版本格式。
2. **更新日志：** 已经完成和发布的真实变化，按时间线显示。
3. **更新预告 / 维护公告：** 下一版功能或临时关闭通知，可设置生效时间；预计时间可以留空。
4. **开发路线图：** 想法、计划中、开发中、已完成、搁置，明确不等于发布承诺。

支持 Markdown 正文、截图、草稿、发布与撤回。较长的规则、日志或公告可以发布独立详情 URL；简短内容内嵌项目详情即可，避免制造大量空内容页面。

### 4.3 游戏中心（Games）

- 游戏属于 Projects 的一种类别；项目介绍、Logo、手动状态和版本只有一份数据。
- 游戏中心额外展示进入游戏、玩法说明、联机方式、统一账号入口、个人战绩和公开统计。
- 旧游戏逐个接入统一账号，优先保留游客模式、房间令牌及原有重连行为。
- 用户成绩仅在取得游戏服务真实授权数据时展示，不能直接从主站修改结算结果。

### 4.4 博客动态（Content）

- 通过 WordPress REST API 或 Feed 获取标题、摘要、原文 URL、封面、分类和发布时间。
- 主站支持展示篇数、显示顺序、精选文章、刷新状态和错误信息。
- 博客内容仍在子比后台编辑；主站不重新保存博客全文作为另一份原创文章。
- 博客 API 不可用时保留最近成功同步的公开摘要并标注更新时间。

### 4.5 在线工具（Tools）

首批规划：Markdown → 纯文本、Markdown → Word、Word → Markdown、Markdown → HTML、HTML → Markdown；查询公网 IP / 指定 IP；安全随机密码生成。后续可加入 JSON 格式化、时间戳、Base64 等。

- 默认游客可用；登录仅用于保存偏好或历史记录等个人化能力。
- 密码采用浏览器安全随机数生成，默认不上传、不保存。
- 文档转换尽量本地处理；确需服务端上传时限制类型、尺寸与临时文件有效期，明确告知用户。
- IP 查询限制输入类型与外部 API 使用，不开放任意目标 URL 的服务端抓取，避免 SSRF。
- 每个工具有后台管理卡片、帮助说明及独立 SEO 信息。

### 4.6 备案与页脚

ICP备案号、备案链接、公安备案号、图标、版权及必要说明都由后台维护；正式页面显示真实已取得的信息，遵从实际备案展示要求。

## 5. duanap Studio 后台体验规范

**设计目标：** 不是传统表单堆叠的管理系统，而是精简、清楚、易维护的个人运营工作台。

### 5.1 布局

- 左侧单行分组导航，约 220px 展开、可折叠为仅图标模式。
- 顶部显示当前页面、必要的保存/新建操作、站点预览及用户菜单。
- 中间全宽自适应；不再固定“编辑区 + 右侧手机预览”覆盖所有页面。
- 需要视觉反馈的首页编排/主题页面才使用可开关的实时预览，支持桌面/手机切换。
- 卡片圆角约 16–20px，卡片间距约 16–20px；浅色为默认、深色可选；动效克制且支持减少动态效果。

### 5.2 导航分组

| 分组 | 页面 |
| --- | --- |
| 工作台 | 仪表盘 |
| 内容管理 | 首页编排、关于我、项目与作品、博客、在线工具 |
| 用户与游戏 | 游戏中心、用户概览、积分签到概览、机器人接入 |
| 数据与运营 | 网站统计、EdgeOne、搜索优化 |
| 系统管理 | 集成中心、外观主题、媒体库、站点与备案、账号安全、备份 |

### 5.3 页面对应最佳布局

- **项目、工具、游戏：** 默认卡片网格，支持搜索、筛选、排序及列表切换；点击进入完整编辑页。
- **个人资料、社交信息、备案：** 独立卡片。备案采用 ICP 与公安备案两张卡片。
- **SEO：** Meta 与搜索结果预览、搜索引擎接入、Sitemap、robots、RSS 分别成卡片。
- **数据分析：** 指标卡 + 大尺寸趋势图 + 筛选器；同一页面有清晰的统计周期和来源。
- **大量日志和用户记录：** 使用表格与分页，不强行全部改成卡片。
- **备份和恢复：** 概览卡加历史表格，恢复需强确认。

### 5.4 首页编排和 Widget

- 前台模块可启停、排序及选择展示样式。
- 仪表盘 Widget 可启停、排序、选择小/中/大布局；先使用上移下移操作即可。
- Widget 记录数据源、最近成功更新时间、加载中、未配置和异常状态。
- 未接入展示 `— / 未配置`，不得将失败值伪装成 `0`。
- 管理员编辑后需要有未保存提示、成功反馈与危险操作确认。

## 6. 运营数据与第三方集成

| 数据源 | 仪表盘优先展示 | 特别说明 |
| --- | --- | --- |
| 主站 SQLite | PV、链接点击、近期趋势 | 明确统计口径及时间范围 |
| EdgeOne | 请求数、加速流量、缓存命中、安全缓释请求 | **请求数不是独立访客数或 PV**；按域名筛选，展示数据延迟 |
| WordPress | 最新文章、文章总量、分类、同步状态 | 阅读量/点赞量等子比专有字段需确认真实接口 |
| Projects | 项目数、最近更新、手动运营状态、维护预告 | 不将人工状态冒充 HTTP 健康检测 |
| Games | 对局摘要、活跃角色、版本、战绩 | 只读取游戏服务提供的真实聚合值 |
| GitHub | 仓库更新、版本标签和链接 | 不自动覆盖管理员填写的“正式发布版本” |
| 搜索平台 | 网站地图、提交状态、抓取与索引信息 | 接受提交不等于已收录 |

所有外部 API 密钥存放服务端；建立超时、有限重试、按需缓存和失败降级。EdgeOne 能查询到哪些指标取决于现有套餐、权限和 API 实际支持范围。

## 7. SEO、搜索收录与 RSS

**目标：** `duanap.cn` 作为品牌及项目介绍的主要收录入口；`blog.duanap.cn` 继续独立收录原创文章。搜索排名不可保证，提交只帮助发现。

### 7.1 每页 SEO

- 页面级 `title`、`description`、canonical、Open Graph、分享图、robots meta 由统一 SEO Core 生成，可由后台覆盖。
- 首页以 `WebSite`、`Person` 等真实 JSON-LD 描述个人与站点；项目详情按内容使用 `SoftwareApplication` 或合适类型，必要时加入面包屑。
- 所有公开页面提供服务端可读取的 HTML 正文、常规 `<a href>` 内链和独立 canonical。项目卡片优先指向本域真实详情页，不再只通过旧的 `/go/[id]` 统计跳转作为搜索引擎发现渠道。
- `www` / HTTP（若开放）规范重定向至 `https://duanap.cn`；项目 slug 尽量保持稳定，修改需做 301。

### 7.2 robots 与 Sitemap

基础规则建议如下，最终由实际路由与爬虫测试决定：

```txt
User-agent: *
Allow: /
Disallow: /duanap
Disallow: /api/
Disallow: /go/
Sitemap: https://duanap.cn/sitemap.xml
```

- robots 管控抓取，**不是安全授权，也不保证阻止 URL 被索引**。需要公开访问但不应被收录的页面可设置 `noindex`；切勿同时依赖 robots 禁止抓取该页面的 noindex。私人账号和后台首先依靠真实鉴权。
- Sitemap 仅输出公开、已发布、返回 200、具有自身 canonical、允许收录的 URL；项目维护状态不会自动把详情页移出地图。
- `lastmod` 只在重要正文变更时更新，不因项目状态轮询或访问计数而频繁变化。
- 博客使用自己的 Sitemap；主站不把博客文章全文 URL 当作本域原创页面重复发布。

### 7.3 搜索平台

- Bing：验证站点、提交 Sitemap、支持 IndexNow 发布/更新/删除通知。
- 百度：站点验证、Sitemap（依账号能力）、普通收录 API；保留原首页提交功能并扩展已发布 URL。
- 搜狗：站点验证、标准 XML Sitemap；可用提交功能以实际后台权限为准。
- 可预留 Google Search Console 和其他搜索平台适配，但不作为首批阻塞项。
- 后台保留提交结果、错误码、最近请求时间和真实索引情况（若服务商可提供）；提交成功≠索引成功。

### 7.4 RSS

- `https://duanap.cn/feed.xml`：项目更新、正式公告、博客文章摘要的综合订阅。
- `https://blog.duanap.cn/feed/`：WordPress 原始文章订阅地址，需确认实际可用。
- 每条 Feed 有稳定 GUID、真实原文链接、发布日期、摘要及合理的缓存时长。网页声明 Feed 自动发现链接。

## 8. 统一用户、第三方身份与 SSO

### 8.1 主数据归属

- WordPress 用户为最终账号主体；第一次 QQ 网站授权成功后自动创建用户，后续授权进入同一账户。
- QQ 为首选登录按钮；允许绑定 GitHub、Gitee/码云等第三方身份，并可用已绑定身份登录。
- 建议为每个 WordPress 用户生成永久、不可重用的 `hub_uid`（随机 128 位或 UUID），外部游戏只引用它；WordPress 内部 ID 不直接作为长期跨系统契约。
- 第三方身份唯一键包含 `provider + 应用标识 + 该平台签发的稳定 subject/openid`；在插件专用映射表上建立数据库唯一约束。`hub_uid` 同样须有唯一约束，并保留迁移时的稳定映射；不能凭相同昵称、头像、未经验证的邮箱自动合并账号。
- 已被另一用户绑定的身份应拒绝直接覆盖，提供双方验证后合并或人工申诉方案。

### 8.2 SSO 实现边界

**已确定的是“WordPress 做账号主库”，不是“WordPress 已经提供标准 OIDC”。**

- 先验证安全、可维护的 WordPress OAuth/OIDC Provider 与现有子比社交登录能否共存。
- 主站及游戏客户端采用标准授权码 + PKCE；每个应用维护自己的安全会话，不共享整个域名范围的登录 Cookie。Next.js 通过服务端 BFF 或经验证的用户会话调用 WordPress 用户接口，浏览器不直接持有服务端 API Secret，也不在 localStorage 长期保存高权限令牌。
- 登录与积分 API 只接收服务端验证过的身份，客户端自报的 `hub_uid` 不作为授权依据。
- 后台管理员权限单独校验；普通网站账号或外部 QQ/GitHub 登录不自动获得 Studio 管理员权限。
- OIDC 实现若验证失败，记录为架构阻塞并重新选型；不得以复制 WordPress Cookie、裸传 QQ OpenID 或无签名跨域登录链接作为替代。

### 8.3 普通用户中心

展示头像、昵称、公开 ID、第三方账号绑定、积分余额、签到日历、个人游戏角色与战绩、隐私设置；仅对本人开放。用户可查看绑定设备/会话并进行退出与解绑。至少保留一种可用登录方式，并设计失去 QQ 访问权时的账户恢复流程。

## 9. 统一积分、签到与消费

**规则：** 网站、博客、QQ 机器人共享一个 WordPress 账户、一个积分余额、一个每日签到记录，不做三端各自发奖再批量对账。

- 每个 `hub_uid` 每个**北京时间自然日**至多成功领取一次全站每日签到奖励；签到时间数据库保存 UTC，并依据 `Asia/Shanghai` 计算签到日。
- 签到奖励、连续签到天数、积分消费规则尽量复用子比原生业务逻辑；博客原生签到按钮与桥接 API 必须使用兼容的唯一判定。
- 积分变化必须保留原因、业务事件 ID、来源、时间和处理结果；同一业务事件重试不得重复发奖。
- 游戏任务奖励与每日签到属于不同事件类型；修为、游戏币和牌局分数不自动等于网站积分。
- 积分扣减及消费由 WordPress/子比作为唯一写入方负责，小游戏不能直接改 WordPress 数据表。

### 9.1 必须先解决的兼容性问题

子比原生签到函数、积分表/元数据、连续签到和奖励流程必须经**实际安装版本的只读源码审计**确认；公开教程不代表存在稳定的远程 API。桥接插件应优先使用可验证的业务扩展点，不能直接猜字段修改积分。

对于高并发重复签到，需要数据库级唯一业务约束（例如 `hub_uid + 业务类型 + 北京日期`）、短事务和并发测试。若原生积分更新与桥接日志无法处于同一原子事务，应明确采用补偿/对账机制，不能宣称天然强一致。升级子比前应对桥接插件做签到、扣减和连续签到回归测试。

### 9.2 服务不可用时

积分读取可展示标注更新时间的**用户私有缓存**，禁止跨用户共享；签到/兑换必须明确返回失败或处理中，不能先显示“已到账”。跨服务游戏奖励先在游戏端落库，使用唯一事件 ID 发送博客，网络恢复后重试并核对最终账本。

## 10. QQ 机器人及跨端游戏

### 10.1 机器人身份绑定

QQ 互联网页登录身份与 QQ Bot 事件中的用户标识属于不同身份空间，必须分别保存平台、AppID、场景及稳定标识，不直接假设相等。

1. 用户登录主站，在账号中心请求短期有效、一次性、限尝试次数的绑定码。
2. 用户在机器人可用的私聊/授权交互中提交绑定码。
3. 机器人服务端携带自身凭据验证消息身份，通过 WordPress 桥接 API 完成绑定。
4. 同一机器人身份不得无提示绑定多个账号；解绑和换绑需要复核。
5. 已有机器人游客角色可在明确确认后归属到已登录账号，冲突数据按规则保留或迁移，不直接相加。

正式机器人指令及场景权限应以 QQ 机器人开放平台当前的实际授权能力为准。

### 10.2 网页与 QQ 机器人共用修仙游戏

使用**同一个修仙游戏服务端**，两个薄客户端/适配器：网页负责角色卡、背包和图形界面；QQ 机器人负责文字指令与按钮。角色、境界、修为、功法、物品、冷却、战斗由修仙服务端统一校验和写入。

机器人和网页都不得直接修改游戏数据库。服务端执行幂等操作、冷却检查和角色权限校验。WordPress 只管理账号关联与**网站积分**，不承载每次修炼和战斗的高频写入。

### 10.3 旧游戏迁移

先建立 `旧游戏身份/游客 ID → hub_uid` 映射，允许玩家认领现有记录；不直接删除旧 Cookie、playerToken 或断线重连凭据。按游戏逐一完成灰度验证和回滚。

## 11. 数据库与数据表建议

| 系统 | 存储 | 负责数据 |
| --- | --- | --- |
| 主站 Next.js | SQLite (`better-sqlite3`) | 内容；独立会员库另用 `members.sqlite` 管理主站登录身份、密码/恢复哈希、QQ 映射及博客授权关系 |
| WordPress / 子比 | 现有 MySQL/MariaDB | 博客用户及原生登录关联、积分、签到、消费、文章 |
| Hub Bridge 插件 | WordPress 同库新增专用表 | `hub_uid` 映射、机器人绑定、幂等事件、API 审计（按需） |
| 各小游戏 | 原有 SQLite 或各自存储 | 角色、房间、牌局和游戏战绩 |
| EdgeOne / GitHub | 原平台 | 边缘指标、仓库活动；本地只缓存查询结果 |

**本阶段不迁移 PostgreSQL。** SQLite 足以支持单机小型内容管理；WordPress 继续使用原生支持的 MySQL/MariaDB。后续若出现实测写入瓶颈，再按具体服务重新评估，而非全站统一换库。

主站最小业务实体：`site_settings`、`modules`/`module_settings`、`projects`、`project_entries`（更新/公告/路线图）、`tools`、`integrations`（不直接保存明文 Secret）、`widget_layouts`。原有 `links` 与统计表需经迁移兼容验证，避免清空历史数据。

## 12. API 契约草案（非现有接口）

### 12.1 WordPress Bridge

基地址：`https://blog.duanap.cn/wp-json/duanap-hub/v1`

| 方法与路径 | 作用 | 调用权限 |
| --- | --- | --- |
| `GET /me` | 当前认证用户资料与 `hub_uid` | 本人 |
| `GET /me/points` | 当前积分与更新时间 | 本人 |
| `GET /me/checkin` | 签到状态与连续天数 | 本人 |
| `POST /me/checkin` | 统一每日签到 | 本人、CSRF/令牌保护 |
| `GET /me/points/history` | 本人积分流水 | 本人 |
| `POST /bot/bindings/confirm` | 机器人一次性绑定码核销 | 授权 Bot 服务 |
| `POST /service/rewards` | 经授权的游戏奖励发放 | 授权业务服务、幂等 |
| `GET /service/users/{hub_uid}` | 必要的身份查询 | 精确授权的内部服务 |

接口最终响应格式、错误码及鉴权方案在 OIDC/子比审计后确定。示例 JSON：

```json
{
  "ok": true,
  "user_id": "hub_abc123",
  "points": 120,
  "checked_in_today": true,
  "checked_in_date": "2026-10-10",
  "source": "wordpress",
  "updated_at": "2026-10-10T02:30:00Z"
}
```

其中 `user_id` 仅为示例标识。外部服务发送业务发奖请求时必须携带已验证的服务身份、业务事件 ID 和合法奖励类型；奖励数额与限额由服务端规则判断，不能信任客户端自行传入的金额。

### 12.2 统一错误与数据约定

- 401：身份未认证；403：无权操作；409：重复绑定/业务冲突；422：参数不合规；429：限流；503：依赖服务不可用。
- WordPress 自定义路由为每个操作配置 `permission_callback`，明确区分本人会话、内部服务与公开读取；严格验证参数。
- 所有时间存 UTC，页面按约定时区显示；每日签到按北京时间。
- API 使用版本号、超时、有限重试与幂等键；写操作记录审计。
- 公开接口只返回必要字段，任何 Token、Secret、未公开玩家信息不得进入响应和日志。

## 13. SEO、内容与用户隐私的边界

- 主站公开个人资料只展示自行设置为公开的项目和字段。
- `/account/*`、后台、签到结果、个人战绩详情、接口返回的私人数据不进入 Sitemap；实际鉴权优先于 robots 指令。
- 博客文章 canonical 继续指向博客原文；主页展示摘要和原文链接。
- 具有足够原创说明的工具和项目独立收录；重复生成的薄内容页不作为收录策略。
- 账号、积分、机器人用户标识属于个人信息，限制保留周期、访问权限和日志范围，提供必要的隐私说明及账户管理能力。

## 14. 部署、性能与运维

- 沿用 **EdgeOne → Nginx → 宝塔中的 Node.js / PHP 应用**；主站与 WordPress 可运行在同一服务器，但进程与数据目录分离。
- 主站 Next.js Node runtime、SQLite WAL、数据库迁移与本地媒体按现有架构延续；博客保留 PHP + MySQL/MariaDB。
- CDN 缓存只覆盖匿名公开页面和可长期缓存的静态资源；登录、用户资料、签到、积分和鉴权回调响应标记为 `private/no-store`，不得被公共缓存复用。
- 定时任务优先使用宝塔计划任务或轻量系统计划任务；首期不要求 Redis、RabbitMQ、Kubernetes、Docker。
- 业务监控至少覆盖主站健康、WordPress API 连通性、关键签到请求、备份结果及 API 同步失败。
- 数据库、媒体与必要配置密钥分别备份；WordPress 数据库与上传文件须支持一致性恢复。升级前备份，回滚要有验证步骤。
- 重要页面要支持移动端，优先 SSR、延迟加载非关键 Widget、图片优化和合理的 API 缓存。

## 15. 开发边界与权限安全

- OAuth/OIDC 使用授权码与 PKCE，严格验证 `state`、回调 URI、签发方、受众与令牌签名；敏感凭据仅在服务端。
- 用户不能通过传 `hub_uid` 或 QQ 号码冒充他人；积分余额由 WordPress 权威返回。
- 管理后台和普通用户身份分离，管理员操作需独立鉴权、操作审计和二次确认。
- QQ 机器人绑定码短时有效、一次性、限制尝试次数；解绑和身份迁移有冲突处理。
- 游戏服务端必须对所有奖励、冷却与结算进行最终校验；防重复请求与刷积分。
- 上传文件有格式与大小白名单、临时数据清理和安全解析；API 严格限制外部目标，防止 SSRF 和注入。
- EdgeOne/WAF 配置要允许正常搜索抓取与 OAuth 回调，但不因为 User-Agent 自报为爬虫就直接绕过安全机制。

## 17. 关键验收用例

### 17.1 内容和后台

1. 无需修改代码即可更新公开资料、社交入口、ICP备案、项目版本、更新公告及手动状态。
2. 将项目设置为“维护中”后，前台显示说明，原项目介绍与 SEO URL 仍存在。
3. 撤回项目后，公开入口和 Sitemap 正确变化；原有链接按设计返回状态或重定向。
4. 移动端可正常管理常用内容，危险删除和恢复操作需确认。

### 17.2 SEO 与内容

1. 首页、项目详情、工具详情拥有正确、唯一的 Title/Description/Canonical。
2. Sitemap 不含后台、草稿、私有内容、重定向或 404 URL。
3. 浏览器禁用 JavaScript 时，关键公开内容仍可被读取。
4. RSS 条目链接到真实来源，博客全文不在主站重复发布。
5. EdgeOne/WAF 不错误挑战常见搜索爬虫；站长平台提交与实际索引情况分开展示。

### 17.3 账号和积分

1. 主站 QQ 首次授权后创建主站本地用户；博客 UID 仅在用户完成博客授权关联后建立映射。
2. 绑定 GitHub/Gitee 后任一已绑定平台进入同一账号；异常冲突无法自动合并。
3. 博客、主站、QQ 机器人同日依次签到，仅首次发一次奖励。
4. 并发两次签到、网络超时重试、重复机器人消息不增加第二份积分。
5. 游戏发奖失败后能够同事件 ID 安全重试，不能多发或误显示到账。
6. 用户或管理员无法通过更换请求 ID 查询他人积分及绑定信息。

### 17.4 游戏与运维

1. 老游戏用户可以认领既有记录，游客/房间重连能力不退化。
2. 网页和 QQ 机器人对同一修仙角色操作，看到一致的权威游戏数据。
3. WordPress API、EdgeOne API 临时失效时，主站公开页面仍可访问。
4. 生产升级可回滚，且 WordPress、主站和游戏各自的数据备份可验证。

### 18.1 已确定
