# 主站备份与恢复

后台「系统信息」中的备份包含 SQLite 在线一致性快照和本地媒体。快照副本转换为单文件日志模式并清除登录会话、登录失败记录；环境变量、密码哈希和第三方密钥不进入备份。主数据库仍使用 WAL。

备份存储在 `HUB_DATA_DIR/backups/`，列表和下载仅管理员可访问，响应不缓存。归档使用 SHA-256 校验数据库和每个媒体文件；校验用于检测损坏，不代表备份来自可信的人。只恢复自己保管的备份。

图片单文件上限5 MiB，音频单文件上限20 MiB，共最多1000个媒体文件；在线打包预检数据库和媒体总计不超过80 MiB，解压后的JSON上限128 MiB。超过上限时明确拒绝归档，应使用停机磁盘备份，不会静默省略歌曲文件。

仅含图片的归档保持version 1；包含音频使用归档version 2，恢复/回滚均包含原音频及其哈希。旧version 1图片归档继续可读。含音频的version 2归档必须使用本版或更新的恢复脚本；不能用旧程序恢复并假设其支持歌曲文件。数据库schema仍为2，此处归档版本与数据库版本不同。

## 恢复

1. 停止应用进程。将备份下载并存放在持久化目录外，保留原有目录的磁盘备份。
2. 从项目目录执行，替换路径并核对目标。`--confirm-restore` 明确确认替换数据。

```powershell
node scripts/restore-backup.mjs --input "V:/backups/backup.hub.gz" --data-dir "V:/hub-data" --confirm-restore
```

Linux 同样使用绝对路径。脚本验证文件大小、Gzip、编码、哈希、SQLite 完整性、Hub 表结构和媒体路径；拒绝活动进程、符号链接和高于当前应用支持的数据库版本。验证完成后取得维护锁，先在暂存目录写入恢复数据，再替换主数据库与媒体目录。

脚本输出的 `rollback-*` 目录保留替换前的数据，以及可再次使用同一恢复命令的 `rollback.hub.gz`。发生普通文件操作失败时脚本尝试原地撤回，暂存与回滚目录保留供检查。断电或强制杀进程后，不要直接清除目录或启动应用：先检查维护锁、暂存目录和回滚目录，确定完整的一份数据再恢复。

3. 恢复成功后启动应用，检查健康接口、首页、项目、媒体、Sitemap/RSS，再重新登录 Studio。旧会话不会恢复。
4. 如需回滚，停止应用，使用输出目录中的 `rollback.hub.gz` 执行相同恢复命令，再完成检查。

一个持久化目录只允许一个应用进程取得运行锁。此版本不支持多个 Node 实例共享同一个数据目录进行发布切流。

## 本地演练

```powershell
npm run test:backup
```

测试只操作独立临时目录，13 项用例验证损坏/越界与无效表结构拒绝、实际内容和媒体恢复、活动进程拒绝、schema 2 升级/快照及冲突旧备份拒绝，并实际恢复回滚归档。另注入移动原文件失败及自动回滚失败，检查原数据保留和维护锁屏障。浏览器用例还对首页卡片、歌单与博客开关执行在线备份及隔离恢复/回滚。WordPress 摘要缓存可重建，随内容库归档但不代表博客正文；独立会员按专用脚本另外备份。生产备份的恢复能力仍需在正式部署环境另行演练。
