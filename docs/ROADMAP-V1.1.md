# 三阶段渐进式开发与上线计划 V1.1

> **覆盖原需求文档第 16 章中不再适用的开发顺序。** 产品范围保持 `REQUIREMENTS-V1.0.md`，本文件是最新的交付顺序与验收规则。

## 1. 不可破坏的总体要求

1. 每个阶段都能形成独立可运行、可上线、可回滚的完整主站版本。
2. 第一阶段主站不得要求 WordPress、QQ、游戏服务、EdgeOne、GitHub API 已配置才能启动。
3. 可选模块禁用立即生效；扩展服务维护或超时只影响自己的区域，不连带主站、后台、SEO。
4. 「关闭模块」指**功能开关、路由展示和 API 适配器停止参与**，并非免编译更新任意代码。内置代码更新通过正常部署；外部服务在 API 边界独立升级。
5. 维护项目时保留公开项目详情、版本与公告；「运营状态」由站长手工填写，不冒充 HTTP 在线探测。
6. 不对历史数据库进行猜测性迁移；先备份、只读审核、兼容映射、小流量验收。

### P1 正式上线条件

- **在 WordPress 和全部第三方 API 断网情况下**，主页、About、Projects、已发布详情、Tools、SEO、Studio 可用。
- 不存在无法公开的占位 SEO 内容；已发布项目详情支持真实可见正文。

- 完成生产备份、实际恢复演练、旧链接迁移计划和一键回滚步骤。
- 首次新站部署与替换现有 `duanap.cn` 是两个独立决策；替换生产必须单独批准。

- 并发签到与 API 重试只发一次积分；已有博客用户可绑定，历史积分不丢失。

- 每个扩展单独验证与发布，不能以其他扩展尚未完成作为阻塞条件。

## 5. 验收、上线与回滚

每次发版要验证：公开首页、项目详情、后台管理、Sitemap/Feed、禁用全部扩展后主站可用、至少一种外部 API 故障模拟、数据库备份和回滚。

发版可用宝塔 + Nginx + 单 Node 进程。当前运行锁要求一个数据目录对应一个应用进程，恢复或版本切换需停止旧进程；双实例切流须另行设计数据隔离，不能直接共用 SQLite 数据目录。

**避免事项：** 开发初期不接入 Docker/K8s、微服务网关、Redis 集群、复杂队列或强制 CI；不因预期用户增长提前全站迁移 PostgreSQL。
