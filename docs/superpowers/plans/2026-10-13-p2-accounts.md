# P2 账号与积分分阶段开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 主站与博客共享 WordPress 身份、积分和每日签到，同时保持 P1 与 Studio 独立可用。

**Architecture:** 用户选择优先验证免费 WordPress OAuth2 + S256 PKCE + 自有 Bridge 插件，保持现有部署结构；Hub 通过服务器端适配器提供账号中心，身份由受保护的本人 API 确认。WordPress 保持业务权威，Hub 仅保存独立会话和私有缓存。候选 WP OAuth Server 4.5.2 与主题扩展点在全链路隔离验收后冻结，不默认 OIDC、刷新令牌或付费能力。

**Tech Stack:** 现有 Next.js/React/TypeScript、SQLite；WordPress/PHP 与博客现有数据库；免费 OAuth2 Provider + S256 PKCE + 本人 API；成熟客户端实现按协议使用。不新增生产部署进程或购买身份插件作为默认条件。

**Spec:** `docs/superpowers/specs/2026-10-13-p2-accounts-design.md`。

**Status:** 初稿编写于 2026-10-13；用户已要求在 Markdown 修复后推进 P2，目前执行 P2-0。先完成兼容验证，再冻结其余任务的协议与业务适配细节；不把尚未验证的插件能力写成既定事实。

**用户后续调整（2026-10-14）:** 先修复 P1 项目 Markdown 文本框，使编辑时直接显示格式，并保留源码；夜间模式正文与标题改为白色，保证文字不被遮挡。验收后开始 P2-0。子比已有 QQ 登录，P2 应复用该流程，不在主站建立第二套 QQ 账号注册。

**执行状态:** Markdown 修复已以 `c8d0421` 发布，35 项本地生产回归及服务器隔离验收通过。P2-0 已取得实际版本、启用配置、QQ/签到调用路径、参与表引擎与缓存证据，见 `docs/P2-COMPATIBILITY.md`；候选身份组件探测已完成，完整 Provider/主题联调与协议选型未通过，暂不进入 P2-1 真实接入。用户确认 QQ 应用已审核通过，凭据将稍后在服务器配置。

**隔离验证增量:** 用户选择免费 OAuth2；保护原型现已转为正式 Bridge 0.1.0 候选。全新 WordPress/MariaDB、合成用户和主题读取夹具通过 66 项本人 API 断言、33 项 OAuth 断言（含 3 轮每轮 8 并发、SQL INSERT/DELETE 失败回滚）。完整子比加载/真实 QQ/Redis 兼容仍未验收，生产尚未安装。

**本批范围判定:** 设计允许完整兼容门槛前继续隔离接口开发，因此推进 P2-1 只读候选与可重复测试；不据此标记 P2-0 整体完成或开启生产功能。接口合同见 `integrations/wordpress/duanap-hub-bridge/README.md`。下一批 P2-2 可按此合同进行默认关闭的隔离开发；真实启用仍须补齐主题/QQ 与回退验收。

## Global Constraints

- WordPress 是账号、第三方绑定、`hub_uid`、积分、签到和流水的权威；主站不建立第二套会员或余额账本。
- Studio 密码与管理员会话独立。
- Core 启动及公开页面不请求 WordPress。
- P2 完成主站/博客账号和签到；QQ Bot、游戏认领、文章同步、奖励发放接口属于 P3。
- 不直接修改子比商业主题源码，不从 Hub 直接写 WordPress 表，不提交真实用户数据、第三方密钥或私有源码。
- 一个持久化目录只允许一个 Hub 应用进程；P1 内容数据库模式保持不变。
- 身份库短事务与 Core 内容写入队列独立；网络调用有超时，不能持有 Core 队列等待 WordPress。全部改写接口校验来源与 CSRF，第三方回调按协议校验。
- 只读审计可以开始；插件安装、账号迁移和生产写积分不是本轮计划请求的授权内容。

## Review Focus

1. 同一 QQ 身份的并发首次授权：不能创建两个用户/UID，归 P2-1/P2-3。
2. 网络超时发生在积分已提交之后：不能自动再发奖，归 P2-4。
3. 博客原生按钮和 Hub 同时签到：两条入口都受同一业务约束，归 P2-4。
4. 用户 A 缓存或会话被用户 B 命中：必须隔离，归 P2-2/P2-5。
5. 模块关闭、身份库损坏或博客断网：P1 与 Studio 不能被登录适配器拖垮，归 P2-2/P2-5。

### Task P2-0：先完成只读审计和兼容验证

**Files:** 创建 `docs/P2-COMPATIBILITY.md`（脱敏结论）；具体私有源码位置/配置仅保存在忽略目录的审计记录中。创建获批准的隔离验证脚本与测试方案，不写生产系统。

**Interfaces:** 输入为实际安装版本与源码；输出为 Provider 协议合同、可用登录扩展点、积分/签到调用图、事务/缓存结论以及后续测试环境方案。

- [ ] 核实实际 WordPress/PHP/子比版本及已启用的登录插件，确认 QQ/GitHub/Gitee 应用/回调的可用状态；不输出任何凭据或真实用户标识。
- [ ] 跟踪原生建号、绑定/解绑、签到、奖励、连续签到及积分流水路径，区分稳定钩子和不受支持的内部函数。
- [ ] 完成免费 OAuth2 候选的协议、许可、撤销与子比兼容性验证；明确依赖。使用隔离测试用户验证强制 S256、state、精确回调、授权码重放/并发消费、访问令牌期限和资源权限；免费路线不假定具备 OIDC/刷新。检查 `/oauth/*` 与原生 QQ 的查询变量/路由共存，优先独立 Bridge 授权路径。
- [ ] 检查所有积分写入参与表、事务能力与对象缓存；说明原生入口是否可以安全接入同一业务约束。
- [ ] 记录现有用户/积分的备份和恢复方案，不在本轮复制生产数据到开发仓库。
- [ ] 提交脱敏审计结论，逐条列出已验证、待验证和不满足条件的能力。协议或签到一致性不通过时暂停对应真实接入，更新方案后再实现。

**验收结果:** 必须能够回答「选择哪个 Provider、为何兼容」「绑定唯一性如何保证」「博客原生按钮怎样避免重复发奖」「失败后如何恢复」，并有隔离测试证据。没有证据的结论不能标为通过。

### Task P2-1：Bridge 身份与只读 API

**Files:** 创建 `integrations/wordpress/duanap-hub-bridge/` 下的插件入口、`includes/identity.php`、`includes/permissions.php`、`includes/zibll-adapter.php`、`includes/rest-read.php`；插件测试位于其 `tests/`。不复制主题文件。

**Interfaces:** 提供本人 `GET /me`、`GET /me/points`、`GET /me/checkin`、`GET /me/points/history`。Provider 的用户授权由 P2-0 的合同验证；输出稳定 `hub_uid`、权威业务数据与更新时间。

- [x] 先写唯一 UID、同一 WP 用户重复访问、不存在/停用用户、匿名和越权访问的失败用例。
- [x] 为插件专用映射建立 WP 用户 ID/UID 唯一约束，认证访问按需补齐；隔离原有合成用户余额不变，未补齐生产用户。
- [x] 接入已验证的用户授权与子比读取适配；不提供任意 UID 查询接口。此项仅在读取夹具通过，完整主题仍待联调。
- [x] 使用隔离用户验证本人资料/积分/流水。Hub/Studio 代码未变，不存在 WP 角色赋予 Studio 权限的映射。
- [x] 验证不兼容主题/停用 Provider 返回明确不可用，代码不含商业源码/用户数据。

**隔离完成 / 正式验收待办:** 实际子比、QQ 回跳、Redis 缓存、已有生产账号无损验证和生产备份/停用演练仍待执行；不得把上面的隔离完成项视为 P2 正式上线验收。

**验收结果:** 可只读识别同一账户及其 UID；身份不重复、接口越权被拒绝、原博客功能保持有效。此批不启用签到写入。

### Task P2-2：Hub 登录与只读用户中心

**Files:** 创建 `lib/accounts/{config,provider,store,session,wordpress}.ts`、`app/api/auth/{login,callback,logout}/route.ts`、`app/api/account/` 本人读取路由、`app/account/` 页面及小型账号组件；调整 `lib/modules.ts`、私有响应头与 robots。测试 `tests/accounts-auth.spec.ts`、`tests/accounts-isolation.spec.ts`。

**Interfaces:** 登录适配器消费 P2-0 的标准协议和 P2-1 本人 API。Bridge 的 `hub_uid` 经服务端校验映射为内部 `AccountIdentity { hubUid, displayName, avatarUrl }`，`AccountSession` 仅服务器端存储凭据；`WordPressResult<T>` 区分成功、未认证、不可用和未知结果，界面不接触令牌。

- [ ] 先测试伪造/过期/重复 state、错误/缺失/降级 PKCE、错客户端/错回调、开放回跳、令牌无效/过期、退出后重放与双标签页独立授权。身份只能由权威本人 API 确认，不使用不存在的 ID Token。
- [ ] 实现服务器端授权交换和独立 `hub_user_session`；使用 5 分钟一次性授权事务，会话不超过上游访问令牌期限。免费候选默认 3600 秒，过期重新授权；不引入未确认的刷新能力。
- [ ] 用独立 `accounts.sqlite` 保存会话/加密令牌/用户私有缓存，配置缺失及库损坏只影响账号路径。
- [ ] 提供本人会话查看/撤销；验证退出和撤销的来源/CSRF 校验、用户间隔离与撤销后重放拒绝。会话列表不返回令牌或会话密钥。
- [ ] 配置授权事务、过期会话和私有缓存的清理期限；增加隐私说明及博客账户管理入口，验证日志脱敏与过期数据清理。
- [ ] 提供 `/account` 本人资料、积分、流水和签到只读状态；资料编辑与找回密码进入博客既有流程。
- [ ] 模拟 WordPress 超时/停机、账号功能关闭、缓存换用户，确认 P1 公开路由与 Studio 正常，博客请求挂起期间 Studio 内容写入/备份也不被阻塞。运行类型/构建及现有 35 项 P1/Markdown 用例，再运行账号专项测试。
- [ ] 默认关闭账号模块发布候选版本；隔离登录验证通过后才计划生产启用。

**验收结果:** 普通用户能安全登录/退出和读取自身业务数据，管理员鉴权与公开渲染无耦合。此批没有实际签到按钮发奖行为。

### Task P2-3：第三方绑定和账户恢复

**Files:** 扩展 Bridge `includes/social-bindings.php`；创建 `app/account/bindings/page.tsx`、对应本人绑定路由与 `tests/accounts-bindings.spec.ts`；具体提供方回调与子比扩展点按 P2-0 合同实现。

**Interfaces:** 使用 P2-2 的已验证会话和近期重新认证状态；第三方唯一键固定为 provider/app_id/subject，映射到 P2-1 的 UID。绑定/解绑必须返回冲突或成功，不自动合并。

- [ ] 先测试同 QQ 并发首次授权、重复回调、绑定已有用户、同昵称/邮箱不同身份、被另一用户占用和最后一种登录方式解绑。
- [ ] QQ 首选入口复用博客已验证流程；GitHub/Gitee 绑定完成后通过已绑定平台进入同一 WordPress 用户。
- [ ] 用唯一约束和已审计扩展点处理重复/冲突；不同时维护互相不同步的两套第三方绑定主表。
- [ ] 提供失去 QQ 访问权时的备用登录或博客恢复入口；身份合并与积分合并不在此批自动执行。
- [ ] 验证旧博客账户和原有绑定仍能登录，跨用户操作与错误应用标识被拒绝后提交。

**验收结果:** 一名用户/一个 UID 可通过多个已绑定平台登录；冲突明确、解绑可恢复、旧账户不丢失。

### Task P2-4：统一每日签到

**Files:** Bridge `includes/{checkin,events}.php` 与原生签到扩展点适配；Hub `POST /api/account/checkin`、签到界面和结果查询；插件并发集成测试与 `tests/accounts-checkin.spec.ts`。

**Interfaces:** 用户身份来自 P2-1/P2-2；统一 `CheckinResult` 区分成功、已签到、处理中、失败，含服务端业务日期、稳定回执和权威结果。写入逻辑留在 WordPress，不开放 P3 游戏/Bot 发奖接口。

- [ ] 先写主站/博客原生同时签到、不同请求 ID 重试、同一业务事件重放、事务中途失败、提交后响应丢失的测试。
- [ ] 建立 `hub_uid + event_type + business_date` 唯一约束；北京时间日期由服务端计算，测试 UTC 15:59:59 与 16:00:00 跨日边界。
- [ ] 在已验证的主题扩展点统一原生入口和 API；原生签到状态、积分更新、流水/事件结果以及缓存行为必须一起验证。
- [ ] 事务条件满足时执行短事务；不满足则先交付专门的一致性/对账设计及测试，再决定是否允许正式写入。
- [ ] 超时后按同一业务结果查询；界面不本地累加积分、不把未知结果展示为到账成功。
- [ ] 在隔离数据库确认唯一奖励、连续天数、余额与流水一致。通过原生入口对照与并发测试后提交；未通过则保持生产写入关闭。

**验收结果:** 博客和主站同一北京时间自然日只发一次奖励，包括并发和超时重试。

## 本轮完成边界

这份计划没有确认博客当前插件能力，也没有确定具体 OIDC 包或子比内部函数；这些不是可跳过的实现细节，而是 P2-0 的交付与后续接入门槛。本轮未修改线上博客/账号/积分，也未开始产品实现。

下一步建议先执行 P2-0 的只读审计，再将实际结果补入设计和协议合同，由用户审阅后执行后续开发。
